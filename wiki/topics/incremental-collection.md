# Incremental collection and duplicate lesson review

Collection enumerates eligible project files but opens a source body only when its saved device/inode, size, nanosecond modification/change times, mode, privacy policy, or collection version differs. Reads verify identity before and after. A metadata-only change with unchanged bytes refreshes the private stamp without rescanning or recreating candidates. Changed content still passes the existing scanner, source classification, scrubbing, chunk hashing and provenance tracking. Accepted/rejected dispositions and original evidence remain intact. This is a trusted local optimization, not protection from privileged filesystem or private-state tampering. `harvest --rehash` provides an explicit content audit.

The upgrade seeds stamps once. Actual collection inspected 2,128 source files, reading 10,342,195 bytes, and created zero new candidates. The immediate follow-up dry run enumerated those 2,128 files, skipped all source bodies, read zero body bytes and found no new candidates or unreadable sources. These are local command outcomes, not unattended scheduler proof. The source-body counters do not include toolchain verification or directory discovery.

Exact candidate identities still deduplicate equal chunks and retain every source occurrence. Differently worded lessons require semantic review by the existing curator. `inbox compare <id>` and `inbox compare --file <private-input>` expose the complete compact published-note catalog, including status/version/applicability, and up to six related excerpts. Ranking is based on shared words and is not a semantic verdict. The agent reviews the catalog for equivalent meaning, reads relevant full notes, compares proposed notes with one another and prefers extending an existing destination. Different versions, applicability, evidence or contradictions must remain explicit. Similarity never automatically rejects, accepts, deletes or merges source candidates.

New knowledge proposals require a catalog-digest-bound `deduplication` decision for every changed note, concrete reasons, exact compared-page hashes and relationships accounting for the top three ranked matches and any updated destination. A `same-lesson` decision must use the existing note as its destination. Exact duplicate bodies with the same declared domain, package constraints and applicability are refused; different scopes still require semantic review. Apply/export recheck the current catalog; export also checks the isolated worktree's publication records and bytes. Historical proposal hashes remain verifiable during merge reconciliation, but a legacy proposal without review requires a fresh proposal before new application/export. Decisions enter the immutable proposal digest. Machine checks validate the record and hashes; they do not prove the agent's semantic judgment. The compact catalog fails explicitly above 256 KiB rather than silently truncating coverage. No embedding API, dependency, source registration, other project change, or private-text upload is added.

The comparison command was run against an existing eligible Next.js candidate and returned ten published catalog pages and six related excerpts in a 28,982-byte result. This verifies retrieval, not an independently evaluated paraphrase classifier or a real publication. Runtime privacy/content checks passed with 1,760 files at the initial checkpoint; final wiki/runtime outcomes are in the [change journal](../journal/2026-10-18-incremental-collection.md).

See [automatic knowledge maintenance](./automatic-knowledge-maintenance.md) for the surrounding curation and exact-content publication flow. Delivery is tracked by [issue 49](https://github.com/JFusco/brain/issues/49). No new unattended semantic publication outcome is claimed.

## Daily curator adoption

The saved daily curator prompt explicitly loads this merged procedure from fetched main and runs `inbox compare` for useful candidates and proposed replacement texts before publication. It requires concrete catalog-bound decisions within the existing twelve-candidate total, preserves uncertainty and candidate history, and stops with an actionable dependency if the merged CLI is unavailable. The active schedule and target chat are preserved. Exact prompt readback establishes configuration, not future unattended execution. Local body-read efficiency was demonstrated separately from semantic detection quality.
